# ADR-0014:Python 版本由 vnpy_ctp 的 wheel 矩阵反向决定,钉死 3.13

状态: 生效
日期: 2026-08-30
承重性: **承重** —— 决定全部依赖的可选版本集合。变更会使 `pyproject.toml` 的全部
钉死版本需重新求解,且可能使 vnpy_ctp 不可安装(即实盘链路不可用)

## 背景

`docs/IMPLEMENTATION_PLAN.md` 记录的环境为 Python 3.12.10、vnpy 4.4.0 已装、
vnpy_ctp 未装(记为"实盘接口缺口")。该记录来自另一台 MX250 机器,计划第 40 行
自己注明"4090 机器上需重新核对"。

在实际开发机(RTX 4090 / i5-13600KF)上核对,发现该机只有 Python 3.10.6,且计划
记录的 vnpy 系列包全部未装。于是需要先定解释器版本。

遍历 PyPI 上 vnpy_ctp 的全部发布版本,筛 `win_amd64` wheel:

```
cp310: 15 个版本,最高 6.7.11.3
cp313:  8 个版本,最高 6.7.11.4
cp311: 无
cp312: 无
```

**Windows 上能 pip 安装 vnpy_ctp 的 Python 只有 3.10 与 3.13 两个。** 这同时解释了
另一台机器上 vnpy_ctp 为何一直未装 —— 在 3.12 上它装不上。计划把这条记为"实盘
接口缺口",但没有归因到解释器版本。

上界来自另一处:vnpy 4.4.0 把 PySide6 精确钉死为 `==6.8.2.1`,该版本的 wheel 为
`cp39-abi3` 且声明 `requires_python <3.14`。故 3.13 同时是"有 vnpy_ctp wheel"与
"vnpy 依赖仍可安装"的最高版本。

## 决策

**Python 3.13.11**,由 `.python-version` 与 `pyproject.toml` 的
`requires-python = "==3.13.*"` 双重钉死。vnpy_ctp 取 `6.7.11.4`。

解释器由 uv 安装到用户目录,不进系统 PATH;虚拟环境为项目内 `.venv/`,与系统
既有的 3.10 完全隔离。

pandas 钉死为 `2.3.3` 而非最新的 3.0.x:vnpy 4.4.0 只声明 `pandas>=2.2.3`,语法上
允许 3.0,但那不等于上游验证过 —— pandas 3.0 是含破坏性变更的大版本。

## 理由

3.10 与 3.13 二者取 3.13,理由按权重排列:

1. **3.10 于 2026 年 10 月 EOL,距本决策约两个月。** 本项目 Phase 7 要接入真实
   资金,Phase 8 在数月之后。把一个要长期承载真钱的系统压在两个月后停止安全
   更新的运行时上,是在给自己安排一次非自愿的迁移。
2. **生态已经在往前走。** numpy 最新版要求 `>=3.12`,pandas 最新版要求 `>=3.11`,
   两者都已不再为 3.10 出 wheel。留在 3.10 意味着依赖版本只能越来越旧。
3. **3.13 能拿到最新的 vnpy_ctp 6.7.11.4。** CTP API 因穿透式监管一路
   6.3.x → 6.7.x 变动,落后的版本迟早要升,而升级时机通常不由自己决定。

选择 3.13 的风险已实测排除:`vnpy_ctp==6.7.11.4` 在 3.13.11 上安装并 `import`
成功,PySide6 的 `cp39-abi3` wheel 正常,ta-lib 0.7.1 直接取得 wheel 无需编译。

## 放弃的方案

- **Python 3.10.x + vnpy_ctp 6.7.11.3。** 本机已有 3.10.6,零安装摩擦,且依赖组合
  更接近 vnpy 4.4.0 的开发基线。否决理由是上述第 1、2 条 —— 两个月后 EOL 这件事
  不会因为现在方便而消失,而迁移成本只会随代码量增长。
- **坚持计划记录的 3.12,从 sdist 自行编译 vnpy_ctp。** 需配 MSVC 工具链编译
  pybind11 包装的上期技术 C++ SDK,且每次 CTP 版本升级都要重编。否决理由:
  这正是计划"最可能让项目失败的 5 件事"第 5 条点名的那类工程自娱 —— 本项目
  已识别的最大失败风险是"一个永远不上线的半成品系统"。
- **不钉死小版本,只写 `>=3.13`。** 计划第 8 节要求精确钉死,理由是 vnpy_ctp 的
  wheel 与 Python 小版本、CTP API 版本三者绑定 —— 放宽任何一条,升级出问题时
  就没有可对照的基线。
- **pandas 取最新的 3.0.x。** vnpy 的版本声明允许,但 vnpy 4.4.0 发布时 pandas 3.0
  尚不存在,该组合未经上游验证。回测结果的正确性不值得拿来换一个大版本号。

## 后果

好的方面:

- 实盘链路(vnpy_ctp)现在可安装、可导入,不再是计划记录里的"缺口"
- 运行时在项目预计生命周期内保持受支持状态
- 与系统既有 3.10 环境隔离,互不影响

坏的方面:

- **3.13 上的 vnpy 4.4.0 属于上游未必覆盖的组合。** vnpy 自身是纯 Python 包,风险
  主要落在 PySide6 的 GUI 层;而本项目的 GUI 只做只读监控(ADR-0008),即使
  PySide6 在 3.13 上有问题,影响面也限于 Monitor_Shell,不触及录制与交易。
- **3.14 会破掉 vnpy 的依赖**(PySide6 6.8.2.1 声明 `<3.14`)。下次升级解释器前
  必须先确认 vnpy 是否放宽了该钉死。
- 解释器由 uv 管理而非系统安装,新机器部署需先装 uv。这一条已写入 CLAUDE.md 的
  环境小节。
