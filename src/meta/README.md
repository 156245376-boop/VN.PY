# meta   (层级:L2)

## 职责

某日期下的市场参考事实:合约表、交易日历与时段、费率保证金 SCD-2、合约代码规范化,以及这些事实的 Reference_Data_Store 端口(R3/R27/R30)。

## 公开接口

必须与 `__init__.py` 的 `__all__` 完全一致,由 `tests/test_docs_contract.py` 强制(R26.6)。

- `ReferenceDataStore`
- `SessionKind`
- `SessionWindow`
- `TradingCalendar`
- `TradingDayRecord`
- `TradingSessionSpec`
- `is_combination`
- `is_continuous`
- `split_canonical`
- `to_canonical`
- `to_wire`

## 不变式

- **交易日判定只经 `TradingCalendar.to_trading_day()`**(R3.4)。破坏后果:夜盘归属、
  周五夜盘前滚、节前夜盘停盘各写一份,而 1 分钟 Bar 序列**看起来完全正常**,
  错的是日线聚合、单日亏损限额与结算 PnL。任何 `dt.date()` 或工作日推算都是绕过。
- **合约代码的字符串拼接与截取只出现在 `meta/symbols.py`**(R27.2)。需要品种代码
  去查费率或时段时调 `split_canonical()`,不要写 `symbol[:2]`。
- **时段定义以「交易所 + 大写品种代码」为键,且区间之间不得重叠**。只按品种查依赖
  "各交易所品种代码大写后互不重名"这一未经核对的前提;重叠会让同一时刻命中两个
  窗口,交易日归属与应有 Bar 数都不再唯一。两种错误都不会报错。
- **交易日判定拒绝不带时区的时间戳**。时区转换只应发生在数据源入口(R10.6);
  到这里还不带时区说明上游漏了,按北京时间猜会把 UTC 时刻静默错开 8 小时。
- **参考事实不得经 `data` 读取**(R3.1)。`meta` 拥有 `ReferenceDataStore` 端口与
  其值模型;若改为从 L3 的 `Data_Store` 取,是 L2 反向依赖 L3,分层契约当场破裂,
  且回测路径会被迫拖进行情存储。
- **时段定义必须带生效日期,查询必须给参考日期**(R3.2)。夜盘曾被增设与取消,
  收盘时间有 23:00 / 01:00 / 02:30 之分;不存在"当前时段"这一概念。
- **超出日历覆盖范围一律抛 `CalendarMissing`,不返回推测值**(R3.13)。
  「日期不在覆盖范围内」与「该日不是交易日」是两件事,混淆会让节后第一天的夜盘
  静默消失。`CalendarMissing` 属停机类:日期覆盖不到时,所有品种都无法判定。
- **单个品种没有时段定义抛 `SessionSpecMissing`,属「记录并跳过」**(R32.7)。
  缺的是一个品种的配置,停机会用它换全市场的数据损失;但调用方必须按品种计数告警,
  因为被跳过的行情补录不回来。

## 禁止 import

- **不得 import vnpy 或 data** —— 参考事实及其存储端口由 meta 自己拥有;若 L2 反向依赖 L3 data,分层契约立即破裂
- **不得 import 策略、委托、回测、实盘状态** —— meta 是被查询方,查询走显式函数调用而非事件(R24.7)

## 为什么这么设计

**交易日判定为什么必须只有一个出口。** 夜盘 21:00–02:30 归属其后的交易日,周五
夜盘归属下周一,节前夜盘整体停盘而非顺延。这三条规则分散实现时,每一处都能自圆
其说,而任一处写错都不会报错 —— 1 分钟 Bar 完全正常,只有跨日聚合的结论错位。
R3.4 因此要求单一函数,`TradingCalendar` 就是它。

**时段为什么按「交易所 + 品种」查。** 夜盘的存在与否和收盘时间都因品种而异
(部分品种无夜盘,收盘时间三档),且随历史变化。只按交易所查会把"该品种有没有夜盘"
这个事实抹平;只按品种查则在两所品种代码重名时静默串用夜盘时间。两个键都要。

**时段的结构不变式为什么放在值类型上,与 `core/types.py` 的取舍相反。** `Bar` 的
OHLC 是否合法随上下文变化(质量检查要保留异常记录,回测要拒单),所以校验不能进
类型;而时段区间的重叠或退化**没有上下文相关的正确解释**,任何一种读法都会让应有
Bar 数静默算错,故在 `__post_init__` 就地拒绝。

**为什么端口只返回原始记录,不提供"下一个交易日"。** 端口的每个实现(生产用
Parquet 适配器、测试替身)若各自实现换日规则,就会写出略有差异的版本。派生逻辑
一律留在 `meta.calendar`,实现方只搬运事实。

## 否决过的方案

- **让 `meta` 从 `data.Data_Store` 读参考数据。** 需求原文曾如此(R3.1 修订前)。
  否决理由:L2 反向依赖 L3 会使 `.importlinter` 的分层契约破裂,且回测会为了读一张
  费率表而打开行情存储(还可能撞上 DuckDB 的排他写锁)。
- **让需求里的 `Data_Store` 同时承载市场数据、参考事实、策略状态与告警记录。**
  否决理由:四类状态的变更频率、写者进程与备份策略完全不同(见 CLAUDE.md 的进程
  写锁分工)。合成一个会让录制器与实盘进程争同一把锁。现由 `data` / `meta` /
  `runtime` / `obs` 分别持有。
- **按交易所提供"默认时段"再按品种覆盖。** 否决理由:两层回退规则会产生"这个品种
  到底用了哪份定义"的隐式问题,而缺失时间段的表现在 Bar 数上只是一个偏小的数字。
  改为一品种一定义,缺失即抛错。
- **用全局单例持有 `ReferenceDataStore`,换取 `to_trading_day(dt, product)` 的简洁。**
  否决理由:全局状态使测试无法注入不同日历,而"构造乱序与跨节假日场景"正是本模块
  唯一需要测试的东西。改为构造时注入。
- **复用 vnpy 的 `ArrayManager` / 交易日历工具。** 见 `indicators/README.md` 与
  ADR-0004:会把交易框架拖进 import 闭包,`meta` 便无法被自研引擎与 research
  notebook 独立使用。

## 已知局限

- **R27.4 的合约有效期校验尚未实现。** `to_canonical` 目前只做语法解析与世纪推断;
  「推断结果与合约挂牌日期、到期日期构成的有效区间一致」需要合约表,随 Phase 4
  落地。该缺口由 `tools/requirements_coverage.py` 如实报出,没有假装已覆盖。
- **市场事实一条都还没核对。** `tests/meta/test_market_facts.py` 的预期值全部标记
  `pending_expected`,当前必然失败(R34.7)。其中包含:周五夜盘归属、春节前夜盘停盘、
  郑商所 3 位年月的世纪、各交易所品种大小写、组合代码形式、螺纹钢应有 Bar 数。
  **这些是 Phase 1 唯一必须由人完成的部分**,依据须为交易所公告原文(ADR-0001)。
- **时段重叠检查对"凌晨窗口"有盲区。** 区间归一到 0–2880 分钟比较,因此一份同时
  声明 `21:00–02:30` 与 `01:00–03:00` 的定义不会被判为重叠,而后者在语义上应属
  前一个交易日。真实时段定义不含这种形状,故未处理;若将来自研引擎需要,应在此
  补一条"非跨零点窗口的起点不得早于 06:00"的校验。
- **每次查询都向端口要一次数据,没有缓存。** `to_trading_day` 一次典型调用会查
  2–3 次(N 日、N±1 日、时段定义)。Phase 2 接入真实存储后需按交易日做记忆化,
  否则录制器在每 tick 调用 `is_in_session` 时会重复查库。
- **`is_in_session` 把集合竞价判为"在时段内"。** 依据是 R3.10 只说"不在任何
  Trading_Session 内"才丢弃,而 R3.12 把集合竞价列为一种时段。竞价行情是否该被
  录制器丢弃,取决于 R5.11 的排除是否只针对 Bar 构建 —— 这一处需在 Phase 2 接入
  真实行情时确认。
