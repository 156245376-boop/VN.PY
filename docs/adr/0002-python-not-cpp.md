# ADR-0002:以 Python 实现,不用 C++

状态: 生效
日期: 2026-08-30
承重性: 承重 —— 决定全项目的技术栈与可用生态。推翻需重写全部代码

## 背景

期货交易系统对延迟敏感,这一常识使 C++ 成为自然的候选语言。需要判断本项目
是否属于该常识适用的场景。

约束条件:

- 开发者一人,借助大语言模型编写绝大部分代码
- 策略决策周期为 1 分钟(60,000ms)
- 国内期货行情为约 500ms 一次的快照,**不是逐笔成交**
- 已识别的最大失败风险是"一个永远不上线的半成品系统"

## 决策

**Python**。CTP 接入使用 `vnpy_ctp`。

## 理由

**核心理由:延迟预算里语言层开销占约 0.0005%,而它要换走的是全部开发速度。**

量化这件事:策略决策周期 60,000ms,语言层在一次决策上的开销差异是微秒量级。
即使 Python 比 C++ 慢 100 倍,在这个预算下也无法观测。

而"低延迟需要 C++"这条常识针对的是**做市与高频**:那里决策周期是微秒,且拼的是
交易所机房里的网卡到网卡。本项目的行情源本身就是 500ms 快照 —— **信息到达速度
已经把延迟下界钉在半秒,任何语言层优化都无法穿透这个下界。**

CTP 接入这一层其实已经是 C++:`vnpy_ctp` 是 pybind11 对上期技术官方 C++ SDK 的
包装,报单路径上的实际执行体是原生代码。选 Python 并不意味着放弃原生性能,而是
把原生代码限制在它真正有价值的那一层。

真正会遇到性能问题的是 tick 级回测(10⁹ 量级事件)。但那里的正确答案也不是手写
C++,而是 Polars / DuckDB / Numba —— 它们的内核同样是原生代码,且开发成本低若干
个数量级。量级上:250 交易日 × 100 合约的 1 分钟 K 线约 860 万根,Numba 编译后
约 2 秒。

生态方面:vn.py 已经处理了 CTP 连接、重连、委托状态机这类脏活。用 C++ 意味着
自己重做一遍,而这部分代码的缺陷会直接表现为资金损失。

## 放弃的方案

- **C++ 全栈。** 否决理由如上:性能收益在本项目的延迟预算内不可观测,而成本是
  开发速度、可用生态、以及自己重写 CTP 状态机所引入的资金风险。对一人项目,
  这是"最可能让项目失败的 5 件事"第 5 条的典型形态。
- **Python 主体 + C++ 写回测内核。** 比全栈 C++ 合理,但**时机错误**:回测内核的
  性能瓶颈要到 Phase 8 才可能出现,而那时正确的第一选择是 Numba 或 Polars。
  在 Phase 0 就引入 C++ 构建链,是为一个尚未测量到的问题付确定的复杂度成本。
  该选项在 Phase 8 有 profile 数据后仍然可选,不必现在决定。
- **Rust。** 与 C++ 同类的取舍,且 CTP 生态更薄 —— 需自己做 FFI 绑定。
- **用 GPU 加速回测(4090 在手)。** 回测是**路径依赖**的:第 2 分钟的持仓取决于
  第 1 分钟的决定,无法把时间轴切给数千个 GPU 核并行。参数扫描虽可并行,但每组
  参数的代码里全是分支判断(突破没?止损没?换月没?),而 GPU 是 32 线程一组
  必须同步执行同一指令,分支一多效率就崩(warp divergence)。860 万根 K 线的量级
  下,数据搬进显存再搬出就超过 Numba 直接算完的 2 秒。**这个量级用 GPU 是净亏。**
  4090 真正的用武之地只有将来的 ML 模型训练与 tick 级大规模因子计算。

## 后果

好的方面:

- 可直接复用 vn.py 的 CTP 接入、委托状态机与回测引擎
- 开发速度允许"每个阶段都有独立可用产出"这一实施节奏
- numpy / Polars / DuckDB 的内核仍是原生代码,数值密集部分不吃亏

坏的方面:

- **GIL 使参数扫描必须用多进程而非多线程**(R15.4 已按此写)。这不是性能问题,
  是进程间数据传递的复杂度成本。
- **类型安全靠 mypy 而非编译器。** 缓解手段是 `disallow_untyped_defs` 全开,
  并把它列入第一级确定性检查(ADR-0001)。
- 若将来真需要 tick 级实时策略,本决策需重新评估。届时的判据是 profile 数据,
  不是直觉。
