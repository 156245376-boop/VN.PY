# ADR-0015:参考事实的端口与交易日判定归 meta,不归 data

状态: 生效
日期: 2026-08-30
承重性: **承重** —— 改动波及 `requirements.md` 的 R3/R6/R22/R25/R30、`meta` 与
`data` 的公开接口,以及回测与实盘读取参考数据的整条路径

## 背景

需求原文把参考数据放在 `Data_Store` 里:R3.1 要求交易时段"从 Data_Store 的参考数据集
读取",R22.1 要求市场事实"由 Data_Store 的参考数据集按生效日期版本化存储",R30 整条
以 `Data_Store` 为主语,R6.2 与 R25.6 还要求同一个 `Data_Store` 承载质量报告、异常
标记、来源记录、**策略状态**与**告警记录**。

同时存在的另一组约束是分层契约(`.importlinter`,R24.2/R24.10):`meta` 在 L2,
`data` 在 L3,import 只能向下。

两条放在一起就自相矛盾:交易时段、交易日历、费率、保证金都是"某日期下的市场参考
事实",属于 `meta` 的职责;若 `meta` 按 R3.1 从 `Data_Store` 取,就是 L2 反向依赖 L3,
分层契约当场破裂。

还有第三个冲突:R6.2 与 R25.6 让 `Data_Store` 同时持有策略状态与告警记录,而
CLAUDE.md 的状态所有权表与进程写锁分工规定这两者分别属于 `runtime` 与 `obs`。
`Data_Store` 若兼持四类状态,录制器、实盘进程与告警推送会争同一把 DuckDB 写锁。

## 决策

**参考事实的读取端口与值模型归 `meta`,不归 `data`。**

- `meta` 拥有 `ReferenceDataStore` Protocol(`coverage` / `trading_days` /
  `session_spec`)与值模型(`TradingSessionSpec` / `SessionWindow` / `TradingDayRecord`)
- `meta` 拥有交易日判定的唯一出口 `TradingCalendar`
- **交易日与时段判定逻辑只在 `meta.calendar` 一处**,端口的实现方只搬运事实,
  不提供"下一个交易日"这类派生方法
- 时段定义以 **(交易所, 大写品种代码)** 为键;品种级缺失抛 `SessionSpecMissing`
  (记录并跳过),日期超出日历覆盖才抛 `CalendarMissing`(停机)
- 交易日判定拒绝不带时区的时间戳,不猜时区
- `Data_Store` 的职责收窄为市场数据:Bar、tick、质量记录、异常标记、来源表、采集台账

同时把 R6.2 / R25.6 的四类状态拆回各自所有者:策略状态归 `runtime`
(`Runtime_State_Store` → `state.db`),告警记录归 `obs`(追加事件流),
参考事实归 `meta`。

## 理由

**核心理由:一份状态的变更频率、写者进程与备份策略决定了它的所有者,而这三者
在四类状态之间完全不同。**

| 状态 | 谁写 | 何时写 | 未备份的后果 |
|---|---|---|---|
| 行情、质量、来源 | 录制器、构建任务 | 常驻 / 收盘后 | 可重录(自录 tick 除外) |
| 参考事实 | 每日 CTP 快照 | 登录时 | 回测用错费率,不报错 |
| 策略状态 | 实盘进程 | 每次状态变更 | 重启后策略状态发散 |
| 告警记录 | 任意模块 | 异常发生时 | 事后无法复盘 |

把它们合成一个 `Data_Store` 的代价不是"不好看",而是**录制器与实盘进程争同一把
DuckDB 排他锁** —— 表现是录制器丢 tick,而丢掉的历史数据买不回来。

`meta` 拥有端口还有第二个好处:参考数据的实现(Phase 2 的 Parquet 适配器、测试替身)
可以自由替换,而判定逻辑一份都不重复。这正是"改一个模块只进一个子文件夹"的兑现。

**为什么时段按「交易所 + 品种」查。** 夜盘的存在与否和收盘时间都因品种而异 ——
部分品种无夜盘,收盘时间有 23:00 / 01:00 / 02:30 三档,且随历史变化(R3.2)。
只按交易所查会把"该品种有没有夜盘"这个事实抹平;只按品种查则依赖"各交易所品种
代码大写后互不重名"这一从未核对的前提,一旦重名就静默串用另一品种的夜盘时间。

**为什么品种级缺失不停机。** R32.3 把"交易日历数据缺失"列为停机类,针对的是日期
覆盖不到、所有品种都无法判定的情形。单个品种没有时段定义只影响该品种;若同样停机,
录制器收到一个未配置品种的行情就会冻结全市场,而自录 tick 丢了买不回来。故二者
分成两个异常类型,处置方式由类型直接确定(R32.2)。

**为什么端口不提供"下一个交易日"。** 端口若提供派生方法,生产适配器与测试替身
会各自实现换日规则并逐渐分叉。派生逻辑一律留在 `meta.calendar`,实现方只返回原始
记录。

## 放弃的方案

- **让 `meta` 从 `data.Data_Store` 读参考数据(需求原文的做法)。** 否决理由:
  L2 反向依赖 L3 使分层契约破裂;且回测会为了读一张费率表而打开行情存储,
  在回测 read-only 与录制器写锁的约束下引入无谓的耦合。
- **把 `ReferenceDataStore` 放在 `data`,由 `meta` 依赖 `data` 的公开接口。**
  否决理由:方向仍然向上。分层契约只检查 import 方向,不检查"是否只用了公开名",
  所以这条在机械检查下会以违规形式暴露,而不是被容忍。
- **在 `core`(L0)定义端口,两边都依赖它。** 否决理由:`core` 被明文禁止知道交易所
  规则与时段这类领域概念(见 `core/README.md` 的禁止 import)。端口的方法签名
  (`session_spec` 返回 `TradingSessionSpec`)本身就带领域语义,放 L0 会把领域知识
  推到一个所有层都依赖的位置。
- **保留单一 `Data_Store` 但分成四个逻辑命名空间。** 否决理由:命名空间不改变锁的
  粒度,四个命名空间仍在同一个 DuckDB 文件上争写锁,而锁冲突正是这里要解决的
  唯一实际问题。
- **让 `TradingCalendar` 做全局单例,以换取两参数的 `to_trading_day`。** 否决理由:
  全局状态使测试无法注入不同日历,而"跨节假日、夜盘停盘、覆盖边界"恰好是本模块
  唯一需要测试的东西。

## 后果

好的方面:

- 分层契约可机械保持(`meta` 不 import `data`),由 `.importlinter` 持续验证
- 交易日判定只有一处实现,`to_trading_day` 的换日、跨零点、夜盘停盘、覆盖边界
  都有回归测试保护
- 参考数据实现可替换而不触碰判定逻辑;测试可用内存替身,秒级返回
- 四类状态各归其主,录制器与实盘进程不再争同一把写锁

坏的方面:

- **需求文档被改动**:R3.1、R6.2、R6.3、R6.4、R16.6、R22.1、R25.6、R30 的主语从
  `Data_Store` 改为 `Reference_Data_Store` 或各状态所有者。R26.4 要求决策记录只追加
  不修改,所以这次改动记录在本条 ADR 里,而不回写历史
- **`ReferenceDataStore` 的实现要等 Phase 2**。在此之前 `meta` 的判定逻辑只能对着
  内存替身测试,真实日历与时段尚未接入
- **端口的方法集会随 Phase 4 扩张**(`contract` / `params`),届时应作为一次接口
  变更同步 README 与覆盖报告(R26.8)
